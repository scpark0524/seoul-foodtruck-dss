## 1. 핵심 요약(TL;DR)

- **데이터**: 서울 공공데이터 13종(상권·점포·소비·생활인구·교통·기상·공휴일·대기질·시설) + 실시간 citydata.
- **타깃 단위**: **일(日)**. 분기 추정매출을 요일 트렌드(v2)로 일 단위 분해(원본 요일패턴 대비 1/n보다 13배 정확).
- **모델**: XGBoost. **입지 × 업종 × 일자** 매출 회귀. **과거매출(lag) 미사용** → 기록 없는 신규 후보지도 예측 가능.
- **검증**: 시간 holdout(2025) + **leave-dong-out 공간 CV(안 본 행정동) R²≈0.70**.
- **추천 업종**: 푸드트럭 운영 가능 5종(분식·커피/음료·패스트푸드·제과·치킨)으로 한정.
- **서빙**: `src/serve.py` → 추천 메뉴 / 일 예상매출 / 최적입지 + 실시간 현황.
- **웹**: `service_demo/index.html` (요일 선택, 서버 불필요).
- **실시간**: GitHub Actions가 매시간 spot 단위 수집 → 행정동(통합키)으로 변환·누적.

## 2. 문제 정의 & 설계 철학

**목표**: "이 자리에 푸드트럭을 낸다면 어떤 메뉴가 얼마나 팔릴까?"에 데이터로 답한다.

| 의사결정 | 이유 |
|---|---|
| **분기 매출 → 일 단위 분해** | 최종 목표가 일/실시간 서빙. 학습 단위를 서빙 cadence와 일치. |
| **v2(요일 트렌드) 채택** | 원본 '요일별 매출' 정답 대비 v1(1/n)보다 **13배 정확**(§4.3). |
| **과거매출(self-lag) 제외** | ① 기록 없는 *신규 후보지*도 예측해야 입지추천 가능 ② lag가 SHAP를 독점해 "어떤 입지변수가 중요한가"를 가림. |
| **입지×업종 단일 모델** | 한 입지의 업종별 매출을 모두 예측 → 최상위=추천 메뉴, 그 값=예상 매출. |
| **leave-dong-out 공간검증** | "한 번도 안 본 행정동"을 맞히는지 = 신규입지 추천 신뢰도(시간검증만 보면 과대평가). |
| **추천을 푸드트럭 5종으로 한정** | 좌식 레스토랑(한식·양식·중식·일식)·호프는 트럭 운영 불가 → 추천 후보에서 제외. |
| **행정동(8자리) 통합키** | 과거 데이터와 실시간(spot)을 같은 키로 결합. |

데이터별 시간 가용성이 달라 **부분 결측은 NaN 유지**(XGBoost가 결측 자체를 분기 신호로 학습).

### 4.2 로딩·표준화 (`src/data_loader.py`)
- **인코딩 자동 폴백**(utf-8 → cp949), **macOS NFD↔NFC 정규화**, **연·월별 분할 파일 자동 concat**.
- 생활인구 parquet(외국인 21.8M행)은 (행정동×일자)로 집계 후 **`processed/livpop_daily.parquet`로 캐싱**(재로딩 11s→즉시).
- `standardize_sales`로 매출 컬럼 표준화(행정동코드 8자리 zfill, 분기코드 정규화).

### 4.3 추정매출 일자 분해 (v1 vs v2) — 검증 완료
추정매출은 *분기* 단위라 일 서빙용으로 일 단위 분해. 팀이 두 방식 생성:
- **v1**(1/n): 분기매출을 일수로 균등 배분.
- **v2**(weekday trend): 실제 요일 패턴으로 배분.

**원본 파일의 `요일별_매출_금액`(월~일)이 정답**. 요일 프로파일(평균=1) 비교:

| 요일 | 정답 | v1(1/n) | v2 |
|---|---|---|---|
| 금 | 1.15 | 1.00 | 1.15 |
| 일 | 0.80 | 1.00 | 0.81 |

정답 대비 평균절대오차 **v1=0.089 vs v2=0.0067 → v2가 약 13배 정확.** → **v2 채택.**

### 4.4 실시간 데이터 (서울 citydata)
- API: `citydata`(통합) 13개 카테고리 — 실시간 인구/혼잡, **상권 결제(`AREA_SH_PAYMENT_AMT`=매출 프록시)**, 결제자 인구통계, 업종별(RSB) 결제, 날씨·교통 등.
- 대상: 주요장소 **spot 121곳**. 수집: `scripts/collect_realtime.py` (멀티 API키 풀, XML 파싱, 카테고리별 CSV 분리 저장).
- 자동화: `.github/workflows/collector.yml` — **매시간(cron `5 * * * *`) GitHub Actions**가 수집해 repo에 누적.

## 5. 피처 엔지니어링

3개 모듈로 역할 분리:

### `src/features.py` — 분기/정적 집계
소비·상권변화·점포(업종별)·지하철/버스(월→분기)·기상/공휴일/대기질(일→분기)·시설(정적)·생활인구(분기 평균). 행정동명↔코드 매핑(지하철·버스는 코드체계가 달라 동명으로 join).

### `src/features_daily.py` — 일 매출 시계열용(트랙 B)
일 패널 + **캘린더**(연/월/요일/주말/계절 sin·cos) + **매출 lag**(1·7·28·364, roll7/28, 증감) + 일별 외부(기상·공휴일·대기질·생활인구). `LEAKAGE_PREFIXES`로 **요일·시간대·성별·연령 매출 컬럼은 피처에서 제외**(타깃을 쪼갠 값이라 누수).

### `src/features_location.py` — 입지×업종 서비스 코어(트랙 A) ★
- `build_category_panel`: (행정동×업종×분기) + 타깃 = log1p(업종 분기매출).
- `aggregate_storecount_by_category`: **업종별 점포수/유사점포/개·폐업률/프랜차이즈**(=경쟁·시장존재 신호).
- `build_daily_share`: v2에서 (행정동×일)의 *분기 내 일 점유율* 계산.
- `build_location_daily_matrix`: 분기 업종매출 × 일 share → **(행정동×업종×일자) 일 매출** + 캘린더 + 일별 외부. **self-lag 없음.** 메모리 관리 위해 분기별 날짜 표본추출(기본 12일/분기) → **89.2만 행 × 106 피처**.
- 카테고리는 **원-핫**으로 모델에 투입(한 모델이 업종별 매출을 구분 예측).

## 6. 머신러닝 모델 & 학습 로직

### 왜 XGBoost?
표 형식 + 강한 비선형·상호작용 + **결측 자동 처리** + SHAP 해석 + 빠른 학습. 입지×업종 데이터에 최적.

### 트랙 A — 서비스 코어 모델 (`notebooks/06_location_menu_model.py`)
1. `build_location_daily_matrix`로 학습셋 생성(self-lag 없음, 106→튜닝 후 40피처).
2. **검증 ①** 시간 holdout: train ~2024 / test 2025 → R²≈0.90.
3. **검증 ②** **leave-dong-out 공간 CV**(`GroupKFold` by 행정동) → R²≈0.70 (안 본 동네 일반화 = 서비스 신뢰 핵심).
4. 전체로 최종 학습 → `models/xgb_location_daily.{json,pkl}` + `location_daily_feature_cols.json` 저장.
5. **SHAP**(XGBoost 내장 `pred_contribs`)로 핵심 변수 규명.

**최종 하이퍼파라미터**(개선 루프 결과): `max_depth=8, learning_rate=0.03, n_estimators≈600~700, min_child_weight=10, subsample=0.8, colsample_bytree=0.7, reg_alpha=0.1, reg_lambda=1.0, tree_method="hist"`.

### 트랙 B — 일 매출 시계열 (`notebooks/01~05`)
EDA+Naive baseline → 일 피처(lag 포함) → XGBoost(early stopping) → Walk-forward 백테스트(+v1/v2 비교) → SHAP. **기존 점포의 운영 매출 예측용**(lag 활용). 입지추천은 트랙 A가 담당.

### 평가지표 (`src/metrics.py`)
- 회귀: RMSE·MAE·R²·MAPE.
- **입지추천**: Recall@K·NDCG@K·HitRate@K (각 날짜의 매출 Top-K 행정동을 맞히는가).

## 7. 모델 개선 루프(실측 결과)

공간 CV(안 본 행정동) 기준:

| 단계 | 구성 | 공간 CV R² | 결과 |
|---|---|---|---|
| STEP1 베이스라인 | 106 피처, 기본 | 0.696 | 기준선 |
| STEP2 가지치기 | SHAP 상위 40 | 0.693 | ≈동일, **피처 62%↓·속도 2배↑** |
| STEP3 튜닝 | top40 + 튜닝 | **0.705** | 동일분할 비교 **+0.008** |
| STEP4 파생피처 | +경쟁강도 등 | -0.004 | **도움 안 됨 → 폐기** |

교훈: 가지치기로 공짜 효율, 튜닝은 lr↓·트리↑·정규화↑가 유효, 직관적 파생도 반드시 검증.
다음 레버(STEP5): **실시간 `rt_pay_amt`를 보조 타깃/피처로 결합 재학습**(누적 필요).

## 8. 서빙 로직 — 예측이 만들어지는 과정 (`src/serve.py`)

입력: (행정동, 날짜). 출력: 추천 메뉴 + 일 예상매출 + 실시간 현황.

1. **모델·피처 로드**(`xgb_location_daily`, `location_daily_feature_cols.json`).
2. **구조 베이스**: 최신 분기의 (행정동×10업종) 구조 피처(시설·소비·경쟁점포·교통 등) 격자 구성. 점포 없는 조합은 경쟁피처=0(진입 잠재).
3. **캘린더 피처**: 입력 날짜에서 요일·월·계절 sin·cos 계산.
4. **일별 외부**: 그 날짜의 기상·공휴일·대기질·생활인구를 결합(없으면 NaN→모델이 처리).
5. **예측**: 모델 feature 순서로 정렬 → `expm1(predict)` = 업종별 **일 예상매출(원)**.
6. **푸드트럭 5종 필터** → 정렬 → 추천 메뉴. `realtime_dong_daily`에서 최신 실시간 현황(rt_pay_amt 등) 첨부.

API: `recommend_menu(dong, date)` / `predict_sales(dong, cat, date)` / `rank_locations(cat, date, k)` / `location_report(dong, date)`.

## 9. 실시간 데이터 수신 & 행정동 변환

실시간은 **spot(주요장소)** 단위라 backtest 통합키(행정동)로 변환 필요.

1. `scripts/collect_realtime.py` — citydata 13종 매시간 수집 → `raw/realtime/{category}/{날짜}.csv` (GitHub Actions).
2. `scripts/spot_to_dong.py` — **121 spot → 행정동 매핑**(`spot_to_dong.csv`, 120개 코드검증, 신뢰도 high/mid). 서울대공원만 과천이라 제외.
3. `scripts/realtime_to_dong.py` — 누적 CSV를 읽어 **행정동×일자**(`rt_pay_amt`·혼잡·인구·결제 인구통계)와 **행정동×업종×일자**(RSB 업종별 결제)로 집계 → `processed/realtime_dong_daily.parquet`.

→ 과거 모델과 실시간 신호가 같은 키(adstr_cd)로 결합. 상세: `docs/실시간_행정동_연계_가이드.md`.

## 13. 결과 & 핵심 인사이트

- **입지 드라이버(SHAP)**: 유사업종 밀집도 > 업종 점포수 > 업종 정체성 > 프랜차이즈 > 구매력(소비) > 은행·식품소비.
- **요일 효과**(예) 서교동 금요일: 커피-음료 332 > 분식 60 > 제과 42 (백만원/일). 오피스 상권은 주말 급감.
- **최적입지**(예) 커피: 역삼1동·서교동·종로·여의도·명동 — 실제 서울 최대 상권과 일치.
- **추천 업종**: 푸드트럭 가능 5종으로 한정 → 한식음식점이 무조건 1등이던 문제 해결.

## 14. 한계 & 로드맵

- 매출 타깃은 **점포 기반 공공 추정매출**의 일 분해 → 푸드트럭 매출의 *프록시*. **상대 순위(메뉴·입지)는 유효, 절대 금액은 참고치.**
- 일별 변동은 요일·계절까지 반영(분기값의 결정적 분해라 특정일 이벤트·날씨 스파이크는 약함).
- **로드맵**: ① 실시간 결제(`rt_pay_amt`) 누적 → 보조 타깃/피처 재학습(다이나믹화) ② 분위수 예측(불확실성) ③ spot→행정동 좌표 기반 정밀 매핑 ④ 지도 시각화.
